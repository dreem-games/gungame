## Протокол и транспорт (обновлённые условия, 03.09.2026)

Контекст изменился: **интернет непостоянной устойчивости** (не только LAN), **рост частоты снапшотов**,
**сотни игроков на одном сервере**. Прежний вердикт «ws хватает» действовал для LAN/4 игроков и для
этих условий снимается: TCP head-of-line blocking (один потерян
пакет — вся очередь встаёт на 200–500мс retransmission-RTT) при частоте 30Hz+ на плохом канале фатален.

Решение — плоскости, а не замена провода:

1. **Контрольный план (надёжный, ordered)** — существующий **WebSocket**: hello/аутентификация,
   join/комната, команды (`fire`, input), критичные уведомления, сигнализинг/fallback всего протокола.
2. **State-план (lossy, latest-wins, растущие частоты)** — кандидат **WebTransport** (HTTP/3-датаграммы
   только для снапшотов; контроль остаётся на WebSocket). Вводить лишь после метрик P-A/P-C:
    - та же родословная UDP/QUIC, но меньше клея: без ICE/STUN/TURN и DTLS-сертификатов — обычный
      HTTP/3-эндпоинт; WebRTC к серверу добавляет ICE-переговоры
      и DTLS-отпечатки сверху ws-сигналинга, а его серверные стеки (Janus/mediasoup) — конференц-форма;
    - поддержка браузеров неравномерна ⇒ **ws-fallback — требование дизайна**, не страховка:
      feature-detect `typeof WebTransport === 'function'`,
      иначе тот же протокол по ws (медленнее на плохом канале, но играется);
    - WebRTC остаётся инструментом выбора для отдельной фичи — **голосового чата** (аудио/видео).
3. **Прикладной слой — настоящий фикс «частоты растут, задержки не растут»:**

- `tick` (S3) + версионные огибающие + **delta-снапшоты**; текущая реализация оставляет JSON и использует
  штатный `permessage-deflate`, бинаризация вводится только если последующие метрики этого потребуют;
- **адаптивная интерполяция на клиенте**: кольцевой буфер, delay = clamp(k·RTT, 40–200мс) (поглощает
  п. 13): потеря пакета = пропущенный сэмпл, не stall — на TCP такое невозможно;
- сервер: 30Hz + per-соединение backpressure; при congestion частота не повышается, тики coalesce
  до latest baseline, transient events сохраняются в per-client очереди.

**Сотни игроков — никакому транспорту N² не спасёт.** Полный broadcast 100 игроков × 30Hz ≈
150–300 Мбит/с исходящего с сервера. Поэтому state-план нарезается **интерест-менеджментом:**
комнаты-лобби (N матчей) или секторы одной арены — клиент получает только своё окружение
(S4/interest management из «Швов», п. 23). Горизонтальное масштабирование — только после
профилирования CPU одного процесса.

Фазирование (все стадии обратно совместимы, версия `v` в огибающей; текущий ws-протокол продолжает
работать, пока P-B/P-C не введены):

- **P-A — п. 21**: протокол v2 над ТЕКУЩИМ ws (tick, огибающие, дельты, адаптивная интерполяция,
  resync+backoff, адаптация частоты). Уже на этом большинстве сценариев WAN стабилизируется.
- **P-C — п. 23**: комнаты/секторы + маршрутизация; это основной ограничитель трафика для сотен игроков.
- **P-B — п. 22**: только если метрики после P-A/P-C показывают TCP HoL-проблему — WebTransport-data-plane
    - ws-fallback + операционка (UDP/443, TLS1.3-сертификаты).
